# MensVibe Developer Guide

Welcome to the MensVibe codebase. This guide explains the project architecture, tech stack, and common workflows.

## Architecture Overview

MensVibe is a classic MERN stack application:

- **Frontend (`/client`)**: React 19 application built with Vite. Uses Tailwind CSS 4 for styling and Framer Motion for animations.
- **Backend (`/server`)**: Node.js Express API. Uses Mongoose for MongoDB modeling and JWT for authentication.

### Data Flow

1. User interacts with the React frontend.
2. Frontend calls services in `client/src/services/` using an Axios instance configured in `api.js`.
3. Backend receives requests in `server/routes/`, which are handled by `server/controllers/`.
4. Controllers interact with `server/models/` to perform database operations.
5. Responses are returned using a standardized `ApiResponse` utility.

## Key Features Implementation

### Authentication
- Uses JWT (JSON Web Tokens) stored in `localStorage`.
- `AuthContext.jsx` manages global user state and provides `loginUser`, `registerUser`, and `logoutUser` functions.
- `auth.middleware.js` on the backend verifies tokens for protected routes.

### Shopping Cart
- Persisted in MongoDB for logged-in users.
- `CartContext.jsx` synchronizes local state with the backend.

### Vendor Management (New May 2026)
- **Multi-Vendor Schema:** The `User` model now includes `brandName` and `isActive` for users with the `seller` role.
- **Admin Oversight:** Admins can manage the vendor ecosystem via `/admin/vendors`, allowing for merchant suspension and performance analysis.
- **Data Aggregation:** Vendor profiles use complex MongoDB aggregations (via `user.controller.js`) to calculate real-time revenue and active order counts by filtering global orders for specific vendor product IDs.

### Wishlist
- Added as a persistent feature in `User` model.
- Managed via `WishlistContext.jsx` and `WishlistProvider`.

### Payments (Razorpay)
- Integrated via `payment.controller.js` on the backend and `Cart.jsx` on the frontend.
- Uses `razorpay` Node.js SDK to create orders and verify signatures.

## Development Workflows

### Seeder & Sample Vendors
Run `npm run seed` to populate the DB. The seeder now creates multiple distinct vendor entities (e.g., *MensVibe Originals*, *Nike Authorized*) to test the multi-vendor partitioning logic.

### Adding a New Route
1. Create the page component in `client/src/pages/`.
2. Add the route to `client/src/app/App.jsx`.
3. (If protected) Wrap it with `<ProtectedRoute>`.

### Backend Testing
Run `npm test` in the `server` directory. Tests use `supertest` and an in-memory MongoDB server.

## Maintenance & Cleanup

To keep the codebase clean and efficient, follow these guidelines for removing unwanted files and folders:

### Unused Assets
- Check `client/public/assets/` for images or fonts that are no longer referenced in the code.
- Periodically audit the `client/src/assets` folder for unused local components or styles.

### Build Artifacts
- The `client/dist` and `server/node_modules` folders are generated and should not be committed.
- If you encounter build issues, safely delete `node_modules` and the lock file (`package-lock.json` or `bun.lock`), then run `npm install`.

### Temporary Files
- Remove any `.tmp`, `.log`, or `.env.local` files that are not part of the standard configuration.
- Clean up any manual database backups or CSV export files stored outside the `docs/` folder.

### Database Cleanup
- Use `npm run seed` to reset the database to a clean state with sample data.
- To wipe everything, use the `server/scripts/test_db.js` utility or manually clear collections via MongoDB Atlas/Compass.


# MensVibe Project Architecture & File Dictionary

This is your master cheat sheet. If someone asks you "What does this file do?", you can use this guide to answer them confidently without ever looking at the code.

## 📂 The Backend (`server/`)
This is the "Brain" of the platform. It handles data, security, and logic.

### `models/` (The Database Tables)
*Think of these as the blueprints for what information we store.*
* `user.model.js` - Stores all users (Customers, Vendors, Admins) and vendor storefront settings.
* `product.model.js` - Stores the core details of an item being sold (title, description, base price).
* `variant.model.js` - Stores specific versions of a product (e.g., Red/Large vs Blue/Small) and their exact stock.
* `order.model.js` - Tracks everything about a purchase (who bought it, what they bought, shipping address, and return/RMA status).
* `ledger.model.js` - The financial accounting book. Tracks vendor sales and the 10% platform commission fee.
* `affiliateLink.model.js` - Tracks the custom marketing URLs generated by vendors and counts the clicks/conversions.

### `controllers/` (The Managers)
*Think of these as the managers that receive a request from the frontend and decide what to do with it.*
* `auth.controller.js` - Handles Logins, Registrations, and securely checking passwords.
* `order.controller.js` - Handles the checkout process, deducting stock, and approving/rejecting returns.
* `billing.controller.js` - Calculates how much money a vendor has made and how much platform fee was deducted.
* `storefront.controller.js` - Fetches the beautiful, customized public store page for a specific vendor.

### `routes/` (The Traffic Cops)
*Think of these as the maps. When a request comes in (like `/api/v3/orders`), this tells the server which controller to send it to.*
* `order.routes.js`, `user.routes.js`, `billing.routes.js`

### `middleware/` (The Security Guards)
* `auth.middleware.js` - Checks if a user is logged in (via JWT tokens) and if they are allowed to be here (e.g., stopping a Customer from accessing a Vendor page).

## 🎨 The Frontend (`client/`)
This is what the user actually sees and clicks on in their browser.

### `src/app/App.jsx`
The **Master Navigator**. This file holds the entire map of the website. It dictates that if a user goes to `/login`, they see the Login page. 

### `src/pages/` (The Main Screens)
* `Home.jsx` - The main homepage customers see.
* `Shop.jsx` - The main product catalog/search page.
* `Checkout.jsx` - Where customers enter shipping details and place orders.

### `src/pages/admin/` (The Control Panels)
*Currently holds both Admin (platform owner) and Seller (vendor) pages.*
* `SellerDashboard.jsx` - The home screen for a vendor showing their revenue and stats.
* `SellerOrders.jsx` - Where a vendor sees what items they need to pack and ship.
* `SellerBilling.jsx` - The financial ledger page for vendors to see their payouts.
* `SellerStorefront.jsx` - The settings page where vendors upload their banners and set their brand name.
* `SellerAffiliates.jsx` - The marketing page where vendors generate tracking links to share on social media.

### `src/pages/public/` (Public Storefronts)
* `VendorStore.jsx` - The actual public webpage (`/store/nike`) that customers see when they visit a specific vendor's profile.

### `src/components/` (Reusable LEGO Blocks)
* `Navbar.jsx` - The top navigation bar seen on customer pages.
* `SellerLayout.jsx` - The sidebar navigation seen on vendor pages.
* `ProductCard.jsx` - The visual card displaying a product's image and price (used hundreds of times across the site).

### `src/services/` (The Messengers)
*Files like `api.js`, `order.service.js`, `product.service.js`.*
* These files have one job: Send network requests from the Frontend to the Backend (using Axios) and bring the data back.

## 💡 How to explain a feature (Example: Placing an order)
If someone asks: *"How does an order get placed?"*
You can say:
1. "The user clicks buy on the frontend (`Checkout.jsx`)."
2. "The frontend messenger (`order.service.js`) sends the data to the backend."
3. "The traffic cop (`order.routes.js`) routes it to the manager (`order.controller.js`)."
4. "The manager calculates the math, updates the database blueprint (`order.model.js`), deducts the stock, and sends a success message back!"
